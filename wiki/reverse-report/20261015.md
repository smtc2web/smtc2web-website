# 2026年10月15日 smtc2web Windows 安装器卡死 逆向分析报告

| 项目       | 内容                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ |
| 分析对象   | `smtc2web_*_x64-setup.exe`（Tauri v2 / NSIS 安装器）                                                                     |
| 现象       | 安装/卸载时界面卡死在“创建快捷方式”，进程永不退出                                                                        |
| 结论       | `installer_hooks.nsh` 中 **无超时的 `SendMessage(HWND_BROADCAST, WM_SETTINGCHANGE)` 广播**被系统中不泵消息的窗口永久阻塞 |
| 影响版本   | 0.4.4、0.5.4、0.6.5、0.6.6（以及任何含旧 hook 的构建）                                                                   |
| 已修复版本 | **0.6.8**（commit `69bb1e1`，tag `v0.6.8`）                                                                              |
| 验证结果   | 0.6.8 静默安装 **9 秒完成，退出码 0**；0.6.5 静默安装 4 分钟无任何进展                                                   |
| 报告日期   | 2026-10-15                                                                                                               |

## 0. 摘要（TL;DR）

1. 安装器本身**没有损坏**：文件解包、快捷方式（含 AppUserModelID）、`uninstall.exe`、ARP 注册项都已被正确写入。

2. 卡死点在**安装脚本最后阶段的 PATH 注册 hook**：

   ```nsis
   ; installer_hooks.nsh（旧版本）
   SendMessage ${HWND_BROADCAST} ${WM_SETTINGCHANGE} 0 "STR:Environment"
   ```

3. `SendMessage`（无超时）向 `HWND_BROADCAST` 广播时，会**同步等待会话内每一个顶层窗口处理完该消息**。只要存在一个不泵消息的窗口（卡住的 UWP 应用、GPU 覆盖层、安全软件注入的隐藏窗口……），该调用**永不返回** → 安装器主线程阻塞 → 窗口停止响应（WER 记录 `AppHang`）→ 进度停留在最后一行文字“创建快捷方式”。

4. 该缺陷自 `6f7c603`（2026-06-23，首个带 PATH hook 的构建，即 **0.4.4**）起就存在，是否复现取决于**当时系统里有没有僵尸窗口**，因此与安装器版本无关、与系统状态有关。这正好解释“以前更新能装、现在装不上”。

5. **0.6.8 已修复**：广播改为 `SendMessage … /TIMEOUT=1000`（编译为 `SendMessageTimeout`），并把 PATH 写入从 HKLM 改为 currentUser 下的 `HKCU\Environment`。已实测通过。

## 2. 静态逆向

### 2.1 手工解析 NSIS 头部

`0xDEADBEEF` 在文件中出现两次：一次是 stub 代码里的巧合，真正的 NSIS firstheader 位于 PE 覆盖区起始处。

```
0xD400  00 00 00 00            ; flags
0xD404  EF BE AD DE            ; signature
0xD408  4E 75 6C 6C 73 6F 66 74 49 6E 73 74    ; "NullsoftInst"
0xD414  AA 44 01 00            ; header size      = 83114
0xD418  DC 76 4D 00            ; stub 之后的长度   = 5076700
0xD41C  5D 00 00 80 00         ; LZMA props (lc=3,lp=0,pb=2, dict=8 MiB)
0xD421  ...                    ; 压缩数据流起点
```

各版本 header size：0.3.2 = 73958，0.4.4 = 80814，0.5.4 = 83124，0.6.5 = 83114，0.6.6 = 83118，0.6.8 = 85116。

### 2.2 解出头部（脚本 + 字符串表）

数据流是**裸 LZMA1，无 EOS 标记**，因此必须显式给出解压长度。用一个 LZMA-alone 外壳即可交给 7-Zip 解压：

```js
// 解出 NSIS header：props + 8 字节长度 + 数据流
const props = buf.subarray(0xD41C, 0xD421);       // 5d 00 00 80 00
const size  = Buffer.alloc(8);
size.writeBigUInt64LE(BigInt(83114 + 20898174));  // header + 全部载荷
fs.writeFileSync('h.lzma', Buffer.concat([props, size, buf.subarray(0xD421)]));
// 7z x h.lzma -o out     -> out/h 的前 83114 字节即 NSIS header
```

> 注意：不能用 `-1`（未知长度）——该流没有结束标记，7-Zip 会直接拒绝；长度给多了会在末尾报一次 `Data Error`，但前面的数据仍然可用。

```
[esp+0]  = 0x768f859b   USER32.dll!SendMessageW+0x9b        ← 返回地址：Sender 是 SendMessage*
[esp+4..]= 0xffff  0x1a  0x0  0x40c5f8  …  0xffff  0x1a  0x0
                 ^^^^^^ HWND_BROADCAST   ^^^^^^ WM_SETTINGCHANGE
```

**堆栈上出现了两次 `0xFFFF` / `0x001A` 参数对**，与字符串表中的常量一一对应：


## 4. 根因

### 4.1 机制

```
安装器主线程
   └─ CreateShortcut / WriteUninstaller   ← 已完成（文件、.lnk、卸载器都已落盘）
   └─ NSIS_HOOK_POSTINSTALL
        └─ SMTC_AddToPath*（写 PATH）
        └─ SendMessage(HWND_BROADCAST, WM_SETTINGCHANGE, 0, "Environment")   ← 在这里永久阻塞
             └─ user32!SendMessageW → win32u!NtUserMessageCall
                  └─ 同步等待会话内每一个顶层窗口
                       └─ 某个窗口的 WndProc 永不返回  ⇒  死等
```

主线程被内核态消息调用阻塞时**不会泵消息**，于是：

* 安装器窗口表现为“未响应”，Windows 生成 `AppHangB1`；
* 详情栏停留在最后一行文字 —— 用户看到的就是“**创建快捷方式**”（hook 是 `POSTINSTALL`，所以快捷方式其实早已创建成功）；
* 被强杀后 `$PLUGINSDIR`（`%TEMP%\ns*.tmp`）不会被清理，留下残留目录。

### 4.2 为什么“以前能装、现在装不上”

缺陷从 0.4.4 起一直在，但**只有系统里存在不泵消息的窗口时才复现**。2026-09-19 那次安装时没有这样的窗口，所以成功；此后（火绒安装、UWP/覆盖层应用增多）系统里出现了这类窗口，于是**所有带旧 hook 的安装器**——哪怕是早已发布、当年能装的 0.4.4/0.5.4——全部卡死。这也是“与版本无关、与环境有关”的直接证明。

### 4.3 为什么卸载器也挂

`NSIS_HOOK_POSTUNINSTALL` 里有同一条广播（旧版本同样无超时），卸载流程走的是同一个断点。

### 4.4 为什么停在“创建快捷方式”

NSIS 的详情文本由指令输出；hook 位于 `POSTINSTALL`（在文件、注册表、快捷方式之后），而在阻塞发生前没有新的 `DetailPrint`，因此界面停在“创建快捷方式”这一行，造成“卡在创建快捷方式”的错觉。

## 7. 处置与建议

**对用户（本机）**

1. 直接使用 **0.6.8 或更高版本**；已装好，无需再动。
2. 若以后仍遇到同类卡死：任务管理器结束 `*setup.exe` / `uninstall.exe`，删除 `%TEMP%\ns*.tmp`，重启后再装。
3. 可临时退出安全软件（火绒）以降低“有窗口不泵消息”的概率，但根因已在 0.6.8 修复。

**对项目**

1. hook 中的广播**必须保留 `/TIMEOUT=`**（安装和卸载两处），并考虑同时使用 `SMTO_ABORTIFHUNG` 语义。
2. **发布 ≥ 0.6.8**。注意自动更新链路：更新时执行的是**新下载的安装器**，所以 0.6.5/0.6.6 用户更新到 0.6.8 是安全的；但**更新到 0.6.6 / 0.6.7 仍会卡死**，需要引导这些用户手动装一次 0.6.8。
3. 建议在安装器文档中说明卡死残留物（`%TEMP%\ns*.tmp`、僵尸 `setup.exe`）的清理方式。
